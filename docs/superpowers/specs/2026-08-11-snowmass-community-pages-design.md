# Snowmass 社区与项目进展子页面设计

## 目标

在现有 Snowmass 中文翻译目录之外新增三张职责清晰的独立子页面：

- `Progress / 项目进展`：用图表和可核查表格展示翻译进度、权利状态与各 Frontier 的工作体量；
- `Contributors / 同行者`：记录已核实的个人贡献者，并为友情赞助和合作机构保留公开申请入口；
- `Guide / 参与指南`：说明社区成员如何翻译、审校、协助申请授权以及分发项目。

主页只提供简洁入口和项目概览，不把三类内容混排成一个长页面。三个子页面沿用现有雾蓝雪山设计、浅深主题与中英文切换，不引入新前端依赖。

## 信息架构与导航

公开站点增加以下路径：

- `/progress/`
- `/contributors/`
- `/guide/`

主页和三个子页面使用同一套顶栏语义。主导航显示“论文目录、项目进展、同行者、参与指南”，保留 GitHub 参与入口、语言切换和主题切换。子页面品牌标识返回首页；当前页面通过 `aria-current="page"` 标识。

移动端不增加汉堡菜单。窄屏隐藏次要文字链接，同时保留品牌、当前页面、语言和主题控制；正文首屏提供返回首页及相邻子页面入口。

## Progress / 项目进展

### 页面层级

采用已确认的“A：图表优先，表格收尾”：

1. 页面标题、数据更新时间和统计口径说明；
2. 四张核心数字卡片；
3. 翻译阶段图与公开权限环形图；
4. 十个 Frontier 的横向体量图；
5. 可排序、可横向滚动的明细表格；
6. 指标解释与权利边界说明。

### 核心指标

首版展示：

- 已建档论文数；
- `publication_allowed: true` 的可公开改编记录数；
- 仍需额外授权的记录数；
- 已公开中文译文数。

数字必须从 `site/data/papers.json` 实时派生，不得把 541、273 或 268 写死在 JavaScript 或 HTML 中。缺字段、`false` 和 `null` 一律按不可公开处理，继续服从既有权利闸门。

### 图表

不引入图表库，使用语义化 HTML 与 CSS 绘制：

- 翻译阶段图：按 `not-started`、`machine-draft`、`human-review`、`published` 展示数量和比例；
- 公开权限环形图：区分可公开改编与当前不可公开全文；
- Frontier 横条图：展示十个 Frontier 的目录记录数，并注明跨 Frontier 论文会重复计入不同学科行。

颜色沿用现有状态语义：松绿色表示已核验或可公开，琥珀色表示等待授权，红色只用于明确拒绝或阻断。图表不能只依赖颜色；每段同时显示文字、数量或百分比。CSS 图形旁保留屏幕阅读器可读的文本数据。

### 统计表格

每个 Frontier 一行，列为：

- 官方缩写与中英文全称；
- 目录论文数；
- 许可允许改编；
- 需要额外授权；
- 机器初译；
- 人工审校；
- 已公开。

默认按官方 Frontier 顺序排列。桌面端保持完整列，移动端允许表格自身横向滚动，不让整个页面产生横向滚动。表头保持可见，所有数值与图表来自同一份派生结果。

### 当前状态的诚实呈现

如果公开数据仍为 541 篇 `not-started` 和 0 篇 `published`，页面如实显示，不用模拟进度填充视觉空间。空阶段显示“0”，并用说明文字表明项目刚进入首批生产翻译阶段。

### 友情赞助

首版不虚构赞助者，显示“开放申请 / 支持计算与传播”。行动按钮通过项目邮箱发起联系，预填邮件主题。未来只有在支持方同意公开名称、展示内容和链接后才加入名单。

### 合作机构

首版不虚构合作机构，显示“开放申请 / 学术与社区协作”。行动按钮通过项目邮箱发起联系。页面明确说明：被列出仅表示对本项目的具体协作或支持，不代表 Snowmass、SLAC、arXiv、论文作者或任何机构为项目背书。

首版不显示虚拟 Logo，不为开放申请卡片使用灰色占位 Logo。未来增加机构图形资产时，需要记录来源和展示许可。

## Guide / 参与指南

页面以四条并列但可独立完成的参与路径组织内容。

### 1. 参与翻译并署名

- 从具备公开改编基础的论文中认领任务；
- 遵守锁定术语表和四阶段翻译流程；
- 在 Pull Request 中记录论文 ID、来源版本、模型和修改范围；
- 经合并后按项目贡献规则署名。

主要按钮进入 `CONTRIBUTING.md`，辅助按钮进入 GitHub Issues。

### 2. 核对、修改并提出建议

- 可修正术语、数字、公式、引用、格式和中文表达；
- 建议必须指向具体论文、段落或可复核依据；
- 小范围问题可提交 Issue，确定性修改可直接提交 Pull Request；
- 人工审校记录继续保留在论文元数据中。

### 3. 协助申请翻译权限

- 原作者可直接向项目邮箱提供范围明确的书面授权；
- 作者的合作者、朋友或学术联系人可以帮助转达项目请求；
- 不要求协助者公开作者私人邮箱，也不允许批量骚扰式联系；
- 授权必须由有权许可的人给出，介绍人不能代替权利人作出授权。

敏感联系进入项目邮箱；一般流程说明链接到权利协议。页面不提供绕过 `publication_allowed` 的入口。

### 4. 分发和宣传

- 分享公开网站、公开译文和 GitHub 仓库；
- 可在课程、读书会、研究群体和社交媒体中介绍项目；
- 必须保留“非官方社区项目”说明；
- 不得把等待授权的完整译文或本地隔离产物作为宣传材料分发。

### 社区邀请

页面结尾使用明确但克制的邀请语：“我们非常欢迎社区合作者加入。无论是一处术语修正、一篇完整译文、一次作者引荐，还是一次可靠的项目分享，都会被记录为这条开放知识路径的一部分。”

## 联系与申请规则

- 普通翻译、审校和公开建议使用 GitHub Issues 或 Pull Requests；
- 友情赞助、机构合作、作者授权及含私人联系方式的内容使用项目邮箱；
- 邮件链接预填主题，但不在 URL 中预填敏感正文；
- 页面不承诺自动接受赞助、机构名称或授权，所有申请仍需人工核验。

## 双语、主题与共享前端

三个页面使用共享的子页面脚本处理：

- `?lang=zh` / `?lang=en`、浏览器语言和已保存语言偏好；
- 浅色 / 深色主题切换；
- 页面级中英文文案；
- Progress 数据加载、统计派生和可访问状态提示。

不让目录页的 `app.js` 在子页面运行，因为它依赖筛选器和论文卡片 DOM。子页面使用独立、轻量的共享脚本，避免复制三份语言与主题逻辑。现有目录行为和权利数据结构保持不变。

## 数据与失败处理

- Progress 只读取公开的 `site/data/papers.json`；不读取隔离目录、未发布译文或私人授权通信；
- 数据加载失败时显示可读错误和重试按钮，不留下空白图表或伪造零值；
- 未识别的翻译或授权状态归入“其他 / 待核验”，同时保留总数守恒；
- 所有派生分类的合计必须与去重记录总数一致；
- Frontier 是多值字段，表格行允许交叉计数，但页面总指标始终按论文记录去重。

## 可访问性与响应式要求

- 所有导航、按钮和外链具有明确名称与键盘焦点；
- 图表旁有等价文字，统计表使用真实 `table`、`thead` 和 `th`；
- 环形图和横条图在强制颜色模式或无 CSS 时仍有可读数字；
- 支持 `prefers-reduced-motion`，不添加循环动画；
- 390px 宽度下正文、卡片和按钮不溢出，统计表只在自身容器内滚动；
- 浅色和深色模式保持现有可读对比度及状态色语义。

## 测试与验收标准

1. 主页、Progress、Contributors 和 Guide 之间可以双向导航，当前页面标识正确；
2. 三个子页面均支持中文、英文、浅色、深色及直接分享语言 URL；
3. Progress 的总数、翻译阶段和授权阶段全部由公开数据动态派生，合计守恒；
4. 只有 `publication_allowed === true` 计入可公开改编，缺失、`false` 和 `null` 均计入阻断侧；
5. Frontier 表格涵盖十个官方 Frontier，并清楚说明交叉列入规则；
6. 当前无公开译文时准确显示 0，不伪造完成比例；
7. Contributors 首版只列出已核实的发起人，赞助和机构均为开放申请；
8. Guide 完整覆盖翻译、审校、协助授权、分发宣传四条路径；
9. 不公开 Git 提交邮箱、作者私人联系信息、授权邮件或隔离译文；
10. 既有目录筛选、排序、详情、语言、主题和权利闸门回归测试继续通过；
11. 桌面与移动浏览器视觉检查通过，页面无整体横向滚动；
12. Netlify 生产构建通过后才能发布。
